# WhatsApp AI secretary (wa-bot)

Personal AI secretary + second brain that the owner talks to on WhatsApp (text and voice notes).
Single-user: it only ever answers numbers in OWNER_NUMBERS.

## Architecture
WhatsApp → OpenWA (self-hosted gateway, separate container `openwa-api`) → webhook POST → this bot
→ Groq Whisper (voice transcription) → AI provider (OpenRouter chat completions, or Gemini generateContent, with function calling) → tools → reply via OpenWA REST API.

- `index.js` webhook server (HMAC-verified, `X-OpenWA-Signature`), message handling, WhatsApp commands, reminder scheduler (every 20s)
- `ai.js` provider-independent tool loop (max 6 steps); `AI_PROVIDER=openrouter|gemini`. Providers are flat files because the Dockerfile only copies `*.js`
- `ai-openrouter.js` OpenAI-compatible chat completions; sends ZDR/no-collection routing on every request; retries 429/500/502/503 (2/4/8s), then fallback model; 404 = no allowed endpoint -> fallback; 402 -> `CreditError`; clock moved out of the system prompt (cacheable)
- `ai-gemini.js` the original Gemini path; retries 500/503, falls back to GEMINI_FALLBACK_MODEL; echoes model turns verbatim (thought signatures)
- `ai-common.js` error classes, one-line `[ai]` usage log (also writes `ai_usage`), turn ids, `bus` (spend-limit event)
- `pseudonym.js` pseudonymizes every LLM request in `ai.js` (reply/untrusted/converse): known names (People, Private/People, Profile, WhatsApp contact names; read in code only), phones, emails, addresses and ID/card numbers become per-request tokens like `[PERSON_1]`/`[PERSON_1_FIRST]`/`[PHONE_1]`; tool args and the final reply are restored, tool results hidden again; mapping in memory only, never logged; fails closed (`ai.PrivacyError`). Images/PDFs pass as they are. `/pseudo on|off` (kv), default env `PSEUDONYMIZE` (on). Tests: `scripts/test-pseudonym.js`
- `usage.js` `ai_usage` table, `/usage` report, daily spend guard (`DAILY_SPEND_LIMIT_USD`); `models.js` runtime main model in SQLite kv (`model_main`), OpenRouter model list + prices
- `tools.js` tool declarations (Gemini schema, uppercase types; `openaiTools()` derives the OpenAI format, so tools are defined once) + handlers: reminders, notes, calendar
- `db.js` SQLite via built-in `node:sqlite`: `messages` (chat history), `reminders`
- `google.js` OAuth refresh-token -> access-token cache + `api()` helper (shared by future Gmail tools)
- `calendar.js` Google Calendar list/create/update/delete; tools are only declared when GOOGLE_* env is set
- `google-auth.js` one-time interactive script (Desktop OAuth client, loopback redirect pasted by hand) that prints GOOGLE_REFRESH_TOKEN
- `gmail.js` Gmail search/read/create-draft (no send, by design); tools only declared when GMAIL_ENABLED is set. `unreadDigest` feeds the briefing
- `mailout.js` email send behind a typed yes, modelled on outbox.js; off unless `GMAIL_SEND_ENABLED=true` (needs the gmail.send scope: re-run google-auth.js once). The AI only queues (`send_email`: to/subject/body/reply_to_id, max 5 To addresses, no cc/bcc/attachments, CR/LF in to/subject rejected); `index.js` sends via `users.messages.send` when the owner types yes (15 min expiry, `EMAIL_DAILY_LIMIT` default 5/24h). The owner always sees the exact To, subject and full body. Injection guard in code: once search/read_email ran in the turn (or in that chat within 2h), only the replied-to sender or a `People/` contact email is trusted; any other address shows a warning and needs `yes <address>` typed. Replies set threadId + In-Reply-To/References; non-ASCII subjects are RFC 2047 encoded. `/email` shows or cancels the waiting email. One pending yes at a time (a new email cancels a WhatsApp draft and vice versa). `GOOGLE_TEST_BASE_URL` (google.js) is for the mock tests only
- `outbox.js` WhatsApp messages to other people from the bot's own number. The AI only drafts (`send_whatsapp`); `index.js` sends when the owner replies yes (typed, code-level check, 15 min expiry, `SEND_DAILY_LIMIT`). Names are also looked up in `Private/People` in code only (phone numbers; the AI never sees those notes). Never send from the personal session
- `inbox.js` read-only personal inbox: stores incoming messages from the personal session (SQLite `inbox_messages`, `INBOX_RETENTION_DAYS`, OTP/card numbers redacted), `/inbox` digest via `ai.untrusted()`
- `forward.js` second inbox: direct messages to the BOT's number from non-owners are stored (inbox source `bot`) and relayed to the owner per `/forward replies|all|off` (default replies = only people the bot messaged via outbox). No AI, never answers the sender, rate limited (`FORWARD_PER_SENDER_HOUR`, `FORWARD_TOTAL_HOUR`). `inbox.pending()` / `/pending` / the briefing's "Waiting for your reply" list chats whose newest message is theirs (no AI; needs the personal webhook to include `message.sent`)
- `unread.js` unread detection for the personal session, no AI, GET only (never marks read): OpenWA has no read event for incoming messages (`message.ack` is for our own sent messages), so it polls `GET /sessions/<personal>/chats` (live `unreadCount`, read-only key, 60s cache). `/unread` (name, count, age, redacted preview; muted groups/archived skipped), briefing section, `/pending` split into Unread vs Read-not-answered, and a gentle non-urgent alert for VIP chats unread `UNREAD_VIP_HOURS` (default 3, 0 off; respects quiet hours). Payload shape unverified against a live server. `inbox.needsReply()` (rules, 3 newest messages both ways) drops conversation enders (ok/thanks/bye/emoji, Singlish) from pending lists; only 'unsure' cases go to `ai.untrusted()` as strict yes/no (cached in `reply_check`, `NEEDS_REPLY_AI`, `NEEDS_REPLY_AI_PER_HOUR`, fails closed to pending)
- `alerts.js` the routine check + attention alerts (no AI): meetings with a join link (10 and 2 min before), unanswered urgent wording / VIPs / bursts, missed calls (`call.missed`), waiting-for-reply nudges, intake "allow AI?" suggestions. Texts the owner; urgent + unacknowledged escalates to a phone call via Twilio (`TWILIO_*`, optional, OpenWA cannot place calls). Any owner message acknowledges. Quiet hours, per-hour text cap, daily call cap. `/alerts /ack /vip /watch [now] /triage on|off /callme`. Optional AI triage (`/triage`, default off; kv `triage_on`): `triageMessages()` labels the newest unanswered message per non-VIP chat urgent / needs-reply-today / fyi / ignore via `ai.untrusted()` only (ZDR, no tools, fails closed), strict enum output else rules win, cached per message id in `triage` table, capped by `TRIAGE_PER_HOUR` (12) and the daily spend guard. It can raise a missed urgent, downgrade, or suppress a rules alert; VIPs are never classified, downgraded or suppressed
- `intake.js` new numbers that message the bot get a fixed 4-question form (`/intake on`, default off; no AI) written to their hidden Private/People note. AI chat with an outside person happens ONLY after the owner's `/allow <name>`: tool-less ZDR call (`ai.converse`), links/emails scrubbed, 6/hour 20/day per person, 60/day overall, every exchange shown to the owner, STOP honoured, serialized per person. The owner is suggested `/allow` regularly (max 2/day, every 7 days per person). Automatic replies are stored with source `bot-auto` and never count as the owner answering. Owner-initiated invite: `/intake send <name|number>` or the `send_intake_form` tool only QUEUES an invite (table `intake_invites`, recipient resolved by `outbox.resolve()`); the owner sees the full number and the exact intro + question 1 and confirms with a typed yes (15 min expiry, atomic draft->sending claim, `sending` rows failed at startup, `discardInvitesSince` on a failed turn). Refused while `/intake` is off, for the owner's own number, and for anyone stopped / mid-form / done; `INTAKE_INVITES_PER_DAY` (default 10, 0 removes the tool). One pending yes across WhatsApp drafts, emails and invites. On yes the `intake_people` row is inserted first (so replies continue the form and skip the known-person check), then the invite goes out from the bot session; invited numbers are relayed in `/forward replies` mode, and a finished form merges into an existing note by phone without marking it bot-only
- `relationships.js` relationship taxonomy (family, friend, uni-club, classmate, work, past-work, client, service, acquaintance, other) and `/rel` review: the owner's choice sets `reviewed: true` and always wins; keyword hints only help; nothing overrides it
- `wrap.js` evening wrap-up at `WRAP_TIME` (default 21:00, empty disables; `/wrap` runs it now) and birthday-eve reminders, no AI: done today (`tasks.doneOn`), open tasks, tomorrow's calendar/reminders/weather, birthdays tomorrow (`contacts.birthdaysTomorrow`, Feb 29 -> Feb 28 in non-leap years, age only if the year is known), chats waiting for reply, notes created today. Skipped in quiet hours (`alerts.isQuiet`), once a day (kv `last_wrap`), each birthday once per person/year (kv `bday_eve:<name>:<year>`). Birthdays only SUGGEST drafting a message (confirm-to-send in outbox.js). If WRAP_TIME is empty, a standalone birthday text is sent at `BIRTHDAY_TIME` (default 21:00)
- `claude.js` + `claude-bridge/` Claude Code in a SEPARATE container (`claude-bridge`, own network `bridge-net` shared only with wa-bot, env_file `~/OpenWA/claude-bridge.env` = just `BRIDGE_TOKEN`; no wa-bot/.env, no docker socket, repo only as a read-only `.git` mount cloned to its own volume). Two uses: (1) `ai.untrusted(..., {via:'claude'})` for the nightly memory run when `/nightly claude` (or `NIGHTLY_AI=claude`): `claude -p` with `--tools "" --strict-mcp-config --mcp-config '{"mcpServers":{}}' --disallowedTools 'mcp__*' --setting-sources "" --safe-mode` (a bare `--tools ""` still exposed the account's claude.ai connector tools; verified with the real CLI), empty cwd, CLI version pinned in the Dockerfile (bump deliberately and re-check the flags), pseudonymized first, falls back to OpenRouter if the bridge fails; (2) `/code start|status|stop` (owner only) starts `claude remote-control` so the owner drives a tool-enabled session from the Claude app with per-action approval. No WhatsApp text is ever passed to a tool-enabled session. One-time login: `docker exec -it claude-bridge claude` then `/login`
- `retention.js` daily purge (kv `last_retention`) of alerts, triage, reply_check, ai_usage and finished outbox/email_outbox/intake_invites rows older than 90 days; `inbox_messages` is purged by memory.js, kv and chat history are never touched
- `backup.js` + `scripts/backup.sh` daily local backup (host cron): `VACUUM INTO` snapshot of bot.db verified with `integrity_check`, plus the vault WITHOUT its `.git` (holds the sync token), streamed out as one 600-mode .tgz in a 700 folder (`~/backups/wa-bot`), archive verified, 14 days kept, refuses when disk is low. Restore steps are at the end of the script
- `status.js` aggregate bot status for the server dashboard (counts only)
- `memory.js` nightly (`MEMORY_TIME`, default 03:00) + `/memory run`: backfills older 1:1 history from the personal session with `OPENWA_PERSONAL_KEY` (a read-only key; GET requests only), then folds stored messages into `Private/People/<Name>.md` (matched by phone, frontmatter kept, model output validated, SKIP for automated chats) via `ai.untrusted()`. Capped by `MEMORY_NIGHTLY_CHARS`, `MEMORY_BACKFILL_CHATS`, and the daily spend guard; groups are never turned into notes
- `embeddings.js` Gemini embeddings of note chunks in SQLite (`note_chunks`); `vault.searchNotes` merges semantic + keyword hits
- `tts.js` Gemini TTS -> ffmpeg -> OGG/Opus voice notes (only for replies to voice notes when `/voice` is on)
- `weather.js` Open-Meteo forecast (no key); feeds the briefing, `/weather` and the `get_weather` tool
- `contacts.js` contacts as `People/<Name>.md` (frontmatter fields); vCard import (.vcf or a shared WhatsApp contact); birthdays feed the briefing
- `profile.js` `Profile.md`: lasting facts about the owner, injected into every system prompt (3000 char cap)
- `tasks.js` to-do list in `Tasks.md` (Obsidian Tasks syntax); open tasks feed the briefing and `/tasks`
- `scripts/export-chats.js` (not in the image) read-only chat export to Markdown transcripts, run on the owner's own machine
- `graph.js` self-contained HTML map of the vault, sent by `/graph`
- `vault.js` Obsidian-compatible Markdown vault; optional git sync to a private GitHub repo (VAULT_GIT_REMOTE)

## Constraints
- Zero npm dependencies on purpose: Node 22 built-ins only (http, crypto, fetch, FormData, node:sqlite). Ask before adding packages. (System packages in the Dockerfile: git, ffmpeg.)
- Email content is untrusted (prompt injection): the Gmail tools can only draft; sending exists only through `mailout.js` (opt-in, typed yes per email, recipient check after reading email). Never let email text pick a recipient or send without that check.
- AI cost: default is OpenRouter with low-cost models (gpt-6-luna, gemini flash-lite), paid per token; Gemini free tier is the alternative (429 = quota, 503 = busy). Keep token usage lean. Never print, log or commit API keys.
- AI privacy: OpenRouter requests must keep `provider: { zdr: true, data_collection: 'deny', allow_fallbacks: false, require_parameters: true }`.
- Embeddings and TTS still call Gemini directly (`GEMINI_API_KEY`), whatever `AI_PROVIDER` is.
- Notes are the source of truth as `.md` files (owner also edits them in Obsidian). Never store notes only in SQLite.
- Privacy: anything under the vault's top-level `Private/` folder is hidden from the AI (search, read_note, embeddings, find_contact); only `/graph` and Obsidian see it. Chat-derived summaries go there. `BOT_SESSION_ID` pins the bot's own behaviour to its own session. The owner's personal OpenWA session (`PERSONAL_SESSION_ID`) is READ-ONLY: since 2026-10-13 the owner allows a message.received webhook on it, but only for `inbox.js` (store messages, summarize on `/inbox`). Everything from that session is routed to storage before any bot logic; `openwa()` refuses every non-GET call to it; summaries use `ai.untrusted()` (OpenRouter ZDR routing, no tools, fails closed, never Gemini direct); digests are sent directly and not saved to chat memory. `memory.js` may also READ older history from it with the separate read-only `OPENWA_PERSONAL_KEY` and write only to `Private/People`. Do not widen this (no replies from that session, no tools on that text, no non-ZDR models). Automatic messages to outside people exist only as intake.js templates and `/allow`ed AI chats with the limits above; never add a path where text from an outside person reaches a tool-enabled AI call. See `scripts/CHAT_IMPORT.md`.
- Times: owner is in Asia/Colombo (UTC+05:30). Reminders are stored as epoch ms.

## Runtime
- Runs in Docker on an Oracle Cloud Ampere A1 (ARM64, Ubuntu) server, in `~/OpenWA/wa-bot`.
- `docker-compose.override.yml` lives in `~/OpenWA/` and adds the `wa-bot` service on network `openwa-network`, volume `wa-bot-data:/data` (bot.db + vault).
- OpenWA needs `SSRF_ALLOWED_HOSTS=wa-bot` and `RESOLVE_LID_TO_PHONE=true` in `~/OpenWA/.env`.
- OpenWA API docs: https://github.com/rmyndharis/OpenWA/blob/main/docs/06-api-specification.md (webhooks §6.6)

## Commands
- Rebuild + restart: `cd ~/OpenWA && docker compose up -d --build --no-deps wa-bot` (`--no-deps` keeps `openwa-api` running; without it OpenWA restarts and BOTH sessions, the bot's and the personal one, drop; on 2026-10-14 that cost ~25h of inbox messages and the 03:00 memory run)
- Logs: `docker logs -f wa-bot`
- Mock tests: `docker run --rm -v "$PWD":/app -w /app node:22-alpine node --disable-warning=ExperimentalWarning scripts/test-mock.js` (plus `scripts/test-alerts.js`, `test-pseudonym.js`, `test-memory.js`, `test-retention.js` on node:22-alpine, and `scripts/test-claude.js` on `node:22.23-slim` because it needs `script`)
- After any restart of `openwa-api` check BOTH sessions: the bot's (`POST /api/sessions/<id>/start` with the bot key) and the personal one (needs an operator key, e.g. dashboard > WhatsApp > Start)
- Syntax check (no node on host): `docker run --rm -v "$PWD":/app -w /app node:22-alpine sh -c 'for f in *.js scripts/*.js; do node --check $f; done'`
- Secrets live in `.env` (never commit it).
